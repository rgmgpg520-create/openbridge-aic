# 需求侧证据：psf/requests 真实提问抽样

> 技术报告「二、1. 需求分析」的一手证据记录。抽样日期 **2026-10-26**，数据源为 GitHub REST API（仓库 `psf/requests`）。逐条分类记录、汇总数据与可复现的查询命令一并保存在本包内。
>
> **结论：真实新手提问中占比最高的是"贴出一段报错问为什么"（47.9%），而本项目开发用例中该类只有 2 条——这是当前测试集最大的结构性缺口。**

## 一、抽样方法与口径

仓库概况：`psf/requests` 共 **4180 条 issue**（不含 Pull Request），其中带 `Question/Not a bug` 标签的共 **71 条**。该标签在仓库中用于标记被判定为"提问、而非缺陷"的 issue，是官方仓库里最接近"新手提问"的现成口径。

| 帧 | 查询 | 总体 | 取用 | 用途 |
|---|---|---|---|---|
| 帧 1（主样本） | `repo:psf/requests is:issue label:"Question/Not a bug"` | 71 条 | **全量 71 条** | 新手提问的类型分布 |
| 帧 2（背景） | `repo:psf/requests is:issue`（按创建时间倒序） | 4180 条 | 最近 60 条（2026-03-01 ~ 2026-10-12） | 当前 issue 的整体结构与标签使用密度 |

分类口径（人工逐条判定，共 5 类）：`报错排查`（贴出具体报错或异常行为并询问原因与解法）、`用法/参数`（询问 API 用法、参数取值、行为语义、版本兼容与安装）、`安全/漏洞`（漏洞报告与安全政策）、`其他`（功能请求、项目状态咨询、非技术问题）、`噪声`（spam）。判定以"提问者主要想知道什么"为准，单条 issue 可能跨类。

## 四、口径与限制（诚实披露）

1. **71 条是"被明确判定为提问"的样本，不等于全部新手提问。** 帧 2 显示最近 60 条 issue 中只有 6 条带任何标签，说明该标签的施用是稀疏的、且带有自动化关闭流程的成分。因此本文的比例描述的是"该标签下提问的结构"，不宜外推为"所有新手提问的结构"。
2. **帧 1 中未出现"贡献流程"与"许可"类提问**，但这不等于需求不存在：#7462、#5101 证明贡献类疑问确实存在，只是通常不带该标签；许可类疑问（能否商用、义务是什么）一般不会提到上游仓库，多发生在使用者自己的项目里。这两类因此无法用本抽样定量，本作品对它们的覆盖依据是文档缺口而非提问统计。
3. 分类为人工判定，逐条判定记录见附录，可按第六节的命令复核。

## 五、对开发用例集的修正建议

数据指出的缺口很集中：**报错排查占真实提问的 47.9%，开发集只占 2 条**。建议下一版把开发用例从 32 条扩到 40 条左右，优先补 8 条 `issue` 类用例，按真实频次排序：

1. SSL 证书校验失败（自签名证书、localhost、企业代理中间证书）
2. `Max retries exceeded with url` 的成因区分（连接失败 / 重试耗尽 / 服务端拒绝）
3. `Read timed out` 与 `timeout` 参数的取值语义（含 `(connect, read)` 元组）
4. 代理不生效：环境变量与显式 `proxies=` 参数的优先级
5. URL 编码被自动转义（`%` 变 `%25`、中文与空格路径）
6. 模块导入冲突（本地文件名与标准库或第三方库重名）
7. `Transfer-Encoding` 与 `Content-Length` 的显式设置行为
8. 多部分表单（`multipart/form-data`）边界与生成器输入

这 8 类的来源都在附录的 71 条里，可逐条对回 issue 编号。

## 附：可直接写入技术报告「二、1. 需求分析」的段落

为确认需求不是主观推断，2026 年 10 月 26 日我们对 Requests 官方仓库（psf/requests，共 4180 条 issue）做了一次抽样统计。以仓库自带的 `Question/Not a bug` 标签为口径——该标签用于标记被判定为"提问、而非缺陷"的 issue——取全量 71 条（2014-12-25 至 2026-09-11），逐条按提问者主要想知道什么归类：报错排查 34 条（47.9%）、用法与参数 26 条（36.6%）、功能请求与项目状态咨询 9 条（12.7%）、安全漏洞 1 条、噪声 1 条。报错排查内部以连接与网络 11 条、SSL 与证书 6 条、超时 3 条、编码与转义 3 条、环境与依赖 2 条为最高频。

这组数据给出两个判断。第一，新手提问的主体是"贴出一段报错，问为什么、怎么办"，其次才是"某个 API 怎么用"。前者必须把源码、测试与维护文档对照起来才能回答，单靠通用模型的既有记忆容易答错——这与我们在效果验证中观测到的基线行为一致（B03 把 Apache-2.0 答成 MIT，B07 的版本号在 3.11、3.12、2.7 之间跳变）。第二，这类提问在上游得到的回应极为有限：71 条中有 54 条（76%）关闭时只有 1 条回复，45 条（63%）带自动化关闭标签，且目前没有一条处于开放状态。上游社区本身也反复提出这一点：#6833 批评把支持请求一律导向 Stack Overflow，对"刚入门的人"尤其不友好；#7462 记录第一次贡献者在仓库根目录找不到 CONTRIBUTING.md（实际位于 .github/ 下）；#7547 建议为常见 SSL 验证错误补充排错文档，至今仍开放。其中 #7462 与 #5101 反映的"贡献与安全文档可达性不足"，与本作品在固定快照中发现的缺口（CONTRIBUTING.md 未指向 SECURITY.md 的私密报告渠道）属于同一模式，说明该问题不是孤例。

据此，我们把检索语料固定为 Requests 的维护文档、源码与测试，并按真实提问结构校准开发用例的分类：当前 32 条开发用例中，用法与参数 6 条、报错排查 2 条、贡献流程 4 条、许可 2 条、安全 3 条、测试 2 条。抽样同时暴露了一个我们此前未意识到的结构性缺口——报错排查占真实提问的 47.9%，在开发用例中却只有 2 条；后续迭代将优先补充 SSL 证书验证、连接超时与重试、代理环境变量、URL 编码转义等八类报错用例。抽样的完整记录、逐条判定与可复现的查询命令见附录。
